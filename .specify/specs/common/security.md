# NovaLeave — Shared Security Requirements

**Version:** 1.2.0  
**Constitution Reference:** NovaLeave — Constitution v4.0.0, §7 (Security), §8 (Auditing)  
**Last Updated:** 2026-07-28  
**Changelog:** v1.2.0 — Added SR-014 (ReturnUrl Validation), SR-015 (Identity Lockout Config). v1.1.0 — Added SR-012 (Logout), SR-013 (Read Session Validity), stamp revalidation interval to SR-005, rate limiting thresholds to SR-006

---

## Overview

This document consolidates security and privacy requirements shared across all NovaLeave features. Individual feature plans MUST reference this document and MUST NOT duplicate these requirements.

---

## SR-001 — Anti-CSRF Protection

Every HTTP request that changes system state (`POST`, `PUT`, `PATCH`, `DELETE`) **must** validate an anti-forgery token generated by the server and rendered in the form. Requests lacking a valid token **must** be rejected with HTTP 400 or 403.

**Implementation:** Global `AutoValidateAntiforgeryToken` filter (Constitution §7.2).

**Testing:** Integration tests verify rejection of requests without valid tokens.

---

## SR-002 — Dedicated Input Models (Over-posting Protection)

Each state-changing operation **must** receive input through a dedicated ViewModel or command object containing **only** the fields required for that operation. Direct binding to Domain entities or Identity entities is prohibited.

**Testing:** Integration tests verify extra fields are ignored or rejected.

---

## SR-003 — Existence Hiding for Unauthorized Access

When an authenticated user requests a resource they are not authorized to view, the system **must** return HTTP 404 (not 403), making "does not exist" and "not authorized" indistinguishable.

**Testing:** Verify identical responses for non-existent and unauthorized resource IDs.

---

## SR-004 — Session Revalidation at Execution Time

Authorization and identity **must** be revalidated at the exact moment a state-changing operation executes. If the session is invalid, expired, or the user no longer holds the required role/status, the operation **must** be rejected (fail-closed).

**Implementation:** Every controller action or handler validates current session state, role, active status, and relationships before executing business logic. Cannot rely on cached claims.

**Testing:** Simulate expired sessions, role removals, and status changes after page load.

---

## SR-005 — Secure Cookie Configuration

Authentication cookies (ASP.NET Core Identity) **must** be configured with:

| Setting | Value |
|---------|-------|
| `HttpOnly` | `true` |
| `Secure` | `true` (production) |
| `SameSite` | `Strict` or `Lax` |
| Sliding expiration | Enabled |
| Absolute lifetime | 8–12 hours |
| Idle timeout | 20 minutes |
| Security stamp revalidation interval | 5 minutes |
| Revocation | Security stamp update on role/status change invalidates cookies |

**Testing:** Verify cookies are not client-accessible, HTTPS-only, and invalidated on role changes/logout.

---

## SR-006 — Rate Limiting

Sensitive endpoints (login, future password reset) **must** apply rate limiting proportional to risk, independent of Identity's lockout mechanism (Constitution §7.2).

**Default Thresholds:**

| Setting | Value |
|---------|-------|
| Algorithm | Sliding window |
| Max requests per window | 5 |
| Window duration | 1 minute |
| Segments per window | 2 (30-second granularity) |
| Scope | Per IP address |
| Response | HTTP 429 with `Retry-After` header |
| Queue limit | 0 (reject immediately, no queuing) |
| Lockout interaction | Rate-limited requests do NOT increment `AccessFailedCount` |

**Configuration keys** (`appsettings.json`):

```json
{
  "RateLimiting": {
    "Login": {
      "PermitLimit": 5,
      "WindowSeconds": 60,
      "SegmentsPerWindow": 2,
      "QueueLimit": 0
    }
  }
}
```

**Implementation:** ASP.NET Core rate limiting middleware (`System.Threading.RateLimiting`) with `SlidingWindowRateLimiter` applied to `/Account/Login` POST only. Thresholds configurable via `appsettings.json` and injectable via `IOptions<RateLimitingOptions>`.

**Testing:** Verify HTTP 429 on 6th request within 60 seconds; verify rejected requests do not increment `AccessFailedCount`; verify `Retry-After` header is present in 429 response.

---

## SR-007 — Generic Error Messages (Information Disclosure Prevention)

Authentication failures **must** return the same generic error message for all failure categories. No internal state (account existence, failure category, lockout status) may be revealed.

**Testing:** Verify identical error message for unknown email, wrong password, inactive account, and locked account.

---

## SR-008 — Audit Logging for Security-Relevant Events

The system **must** log in a tamper-evident audit trail:
- All state transitions (with actor, timestamp, action, result)
- Successful and failed authentication attempts
- Failed authorization attempts (IDOR, cross-role access)
- Logout and session invalidation events

Logs **must not** contain passwords, tokens, or sensitive PII (Constitution §7.3, §8).

**Testing:** Integration tests verify audit records are created with all required fields.

---

## SR-009 — Data Minimization and Privacy Protection

The system **must** collect and store only minimum data necessary. Specifically:
- Login form collects only Email and Password
- `Reason` field visible only to request owner and assigned Approver
- Audit logs contain no passwords or tokens
- Session cookies contain only authentication identifier

**Testing:** Verify no sensitive data in logs, cookies, or UI beyond necessary.

---

## SR-010 — Explicit Confirmation for Final Actions

Approving, rejecting, cancelling, voiding, and expiry are **final and irreversible**. The system **must** require explicit confirmation before executing these actions.

**Implementation:** Confirmation modal/checkbox with clear irreversibility warning. Confirmation token validated server-side.

**Testing:** Verify actions are not executed without explicit confirmation.

---

## SR-011 — Role-Based Access Separation

Only authorized actors (owner, assigned approver) may access resource-specific views or execute state transitions. Access control enforced at the authorization layer (policies), not just UI hiding.

**Testing:** Verify non-owner, non-approver accounts have zero successful invocations outside authorized scope.

---

## SR-012 — Logout Behavior

Logout **must**:
- Remove the authentication cookie from the response
- Invalidate server-side session state for the current device/browser
- Follow Post/Redirect/Get pattern (redirect to `/Account/Login`)
- Record an audit event per SR-008 (`Action: Logout`)

Logout **must not**:
- Require additional confirmation (single-click action)
- Fail silently — user must always reach the login page

**Scope (MVP):** Single-device logout only. Security stamp is NOT updated on normal logout (only on role/status changes per SR-005). Future iterations may add "logout all devices" via stamp rotation.

**Implementation:** `AccountController.Logout` (POST) → `SignOutAsync()` → redirect to Login.

**Testing:** Verify cookie removed, subsequent requests redirect to login, audit record created.

---

## SR-013 — Read-Operation Session Validity

For **read-only** operations (GET requests for dashboards, lists, details), the system relies on the security stamp revalidation interval defined in SR-005 (5 minutes) to detect invalidated sessions.

For **state-changing** operations, SR-004 applies (revalidate at execution time).

This means:
- A user whose status changes to `Inactive` will lose read access within 5 minutes (next stamp check)
- A user whose status changes to `Inactive` will lose write access **immediately** (SR-004 fail-closed)

**Testing:** Verify that after status change, read requests fail within revalidation interval and write requests fail immediately.

---

## SR-014 — ReturnUrl Validation (Open Redirect Prevention)

After successful authentication, if a `ReturnUrl` parameter is present, the system **must** validate that it is a local URL (`Url.IsLocalUrl()`) before redirecting. External or absolute URLs **must** be ignored, defaulting to the role-appropriate dashboard.

**Implementation:** `AccountController.Login` POST validates `ReturnUrl` via `Url.IsLocalUrl()`. If invalid or absent, redirects to default dashboard per role.

**Testing:** Verify that external URLs (e.g., `https://evil.com`) are rejected and user lands on local dashboard.

---

## SR-015 — Identity Lockout Configuration

ASP.NET Core Identity lockout **must** be configured with:

| Setting | Value |
|---------|-------|
| `MaxFailedAccessAttempts` | 5 |
| `DefaultLockoutTimeSpan` | 15 minutes |
| `AllowedForNewUsers` | `true` |

Lockout is **independent** of rate limiting (SR-006). Rate limiting blocks at the middleware level (HTTP 429) before reaching Identity. Lockout blocks at the Identity level after credentials are checked.

**Testing:** Verify account is locked after 5 failed attempts; verify lockout expires after 15 minutes; verify rate limiting and lockout are independent counters.
